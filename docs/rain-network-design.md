# 避雨路网系统设计

## 版本说明

本文档描述的是 **「完整栅格副本」** 方案下的避雨路网。与早期实现相比，当前版本已经：

- 从 `buildings`、`pois`、`underground_maps` 等表中彻底移除了旧的遮雨属性字段（如 `walkway`、`covered`、`sheltered`、`coveredMeters`、`routingCost`、`rain`、`rainPenalty`、`shelterPenalty`、`transitionPenaltyMeters`、`shortExposureMeters`）。这些字段不再参与导航、渲染或管理后台。
- 移除了风雨长廊的专属图层和遮雨范围概念；风雨长廊现在作为普通区域对象保留实际轮廓，点击可查看介绍，但导航不再因它改变路线或代价。
- 地面导航统一使用一张步行栅格，不再按手绘/OSM 来源区分颜色或额外加价；不再使用天气权重、遮雨范围、道路等级或进出地下的附加代价。
- 避雨模式的数据仍然依赖 `server/static.db` 中独立保存的一份完整栅格副本，通过「删除雨天不可走格子」实现，而不是给露天路径增加代价。

> **测试阶段临时逻辑**：当前开发测试版本的「我要避雨！」导航尚未真正使用 `rain.grid` 栅格副本，而是临时改为**强制走地下路线**：自动选取离出发点最近的地下来去出入口进入地下，再选取离终点最近的地下来去出入口回到地面。车辆坡道（`ramp`）等车辆出入口在 rainMode 下也被视为可步行到达。若最近出入口对在地下路网中不可达，则回退到枚举所有出入口组合并选最短路径。该临时逻辑仅用于快速验证，后续会切回正式的避雨栅格导航。

如果数据库是从旧版本迁移而来，可运行 `scripts/remove-rain-data.mjs` 清理残留的遮雨字段。

## 1. 设计目标

系统提供一个独立于普通地面路网的“避雨路网”版本。用户在步行导航中打开“我要避雨！”后，导航不再使用普通地面栅格，而是使用管理员维护的避雨栅格。

避雨路网的核心语义是：

- 普通路网：正常情况下可通行的地面路网；
- 避雨路网：雨天希望保留的可通行路径；
- 管理员可以删除不适合雨天通行的格子，也可以重新恢复某些格子；
- 两个版本使用相同的坐标系、栅格尺寸和寻路算法。

本系统不再使用遮雨范围、雨天权重、道路等级或进出地下附加代价。避雨模式通过**删除不可用路径**实现，而不是给露天路径增加代价。

> 测试阶段：当前「我要避雨！」临时改为强制走地下路线，使用最近出入口，尚未真正切换 `rain.grid`。后续会切回正式的避雨栅格导航。

## 2. 总体架构

```text
public/data/campus.json
        │
        ├── 普通路网：campus.grid
        │
        └── static.db / surface_networks / rain
                │
                └── 避雨路网：rain.grid

前台选择普通/避雨版本
        │
        ├── 普通模式：initRouting(campus.grid) → 地面 Dijkstra
        │
        └── 测试版避雨模式：
                ├── 找到离起点最近的地下来去出入口（含 ramp）
                ├── 找到离终点最近的地下来去出入口
                ├── 地面 → 地下 → 地面
                └── MapView 绘制地面段 + 地下段

管理后台
        │
        ├── 从普通路网或已保存的 rain 路网加载栅格
        ├── Leaflet 图层 + 画笔/擦除
        └── PUT /api/surface-networks/rain
```

系统仍然使用当前地面导航的栅格模型，不引入另一套道路节点和边模型。地下路网 `nodes + edges` 不受本系统影响。

> 测试阶段：前台「我要避雨！」暂时不切换 `rain.grid`，而是直接复用地下集成导航并强制选择地下路线。

## 3. 栅格数据模型

### 3.1 基础结构

普通路网和避雨路网都使用 `Campus.grid`：

```ts
interface SurfaceGrid {
  x0: number
  y0: number
  dx: number
  dy: number
  rows: string[]
}
```

字段含义：

| 字段 | 含义 |
|---|---|
| `x0` | 栅格左侧起始经度 |
| `y0` | 栅格顶部起始纬度 |
| `dx` | 单格经度间隔 |
| `dy` | 单格纬度间隔 |
| `rows` | 栅格行字符串，每个字符代表一个格子 |

当前校园栅格约为 `250 × 172`，每格约 5.4 米。

### 3.2 格子值

普通路网沿用 `campus.json` 的既有数据：

- `0`：可走；
- `2`：历史遗留的另一种道路来源，运行时与普通 `0` 同等视为可走；
- 其他字符：不可走。

避雨路网保存时只允许：

- `0`：避雨模式下可走；
- `1`：避雨模式下不可走。

后台的“画笔”将格子设为 `0`，“擦除”将格子设为 `1`。编辑器从普通路网复制草稿时，会通过 `toRainDraft` 把 `0`/`2` 统一规范化为 `0`，其余统一为 `1`，因此保存的避雨版本只含 `0/1`，不再携带道路来源信息。

### 3.3 版本关系

```text
普通版本：campus.grid
避雨版本：surface_networks.id = 'rain'
```

避雨版本不是对普通文件的覆盖，而是独立保存的完整栅格副本。没有保存过避雨版本时，后台会以普通路网作为编辑初始值；前台此时显示“暂无避雨路网”，不会错误地把普通路网当作已配置的避雨路网。

### 3.4 旧数据迁移

历史版本中曾在 `buildings`、`pois`、`underground_maps` 等表里保存遮雨相关字段。当前版本已废弃这些字段，并提供迁移脚本：

```bash
# 预览（不写库）
node scripts/remove-rain-data.mjs --db server/static.db

# 执行迁移，同时生成独立备份
node scripts/remove-rain-data.mjs --db server/static.db --write --backup server/backups/static-before-remove-rain-$(date +%Y%m%d).db
```

该脚本会：

- 扫描 `buildings`、`pois`、`underground_maps` 表中的 `data` 字段；
- 递归删除所有废弃的遮雨字段；
- 写入前先做 SQLite online backup 并通过 `PRAGMA integrity_check`；
- 在事务中更新记录；
- 不改 `updated_at`，也不改动地下拓扑或其他业务字段。

运行后建议执行一次 `git diff --check` 和数据库完整性检查，再提交 `server/static.db`。

## 4. 数据库存储

避雨路网存储在 `server/static.db` 的 `surface_networks` 表：

```sql
CREATE TABLE surface_networks (
  id TEXT PRIMARY KEY,
  data TEXT NOT NULL,
  updated_at INTEGER NOT NULL
);
```

当前使用的固定记录：

```text
id = 'rain'
```

`data` 是完整的 `SurfaceGrid` JSON，例如：

```json
{
  "x0": 121.6001,
  "y0": 31.1842,
  "dx": 0.00005,
  "dy": 0.00005,
  "rows": [
    "111111000011",
    "111100000011",
    "111111111111"
  ]
}
```

静态地图、地下地图和动态业务仍分别存储，不把避雨路网写入 `dynamic.db`、旧的 `map.db` 或地下地图表。

## 5. 服务端 API

实现文件：

```text
server/surfaceNetworks.mjs
```

### 5.1 获取所有版本

```http
GET /api/surface-networks
```

返回普通版本和已保存的避雨版本：

```json
{
  "default": { "x0": 0, "y0": 0, "dx": 1, "dy": 1, "rows": [] },
  "rain": null,
  "updatedAt": 0
}
```

如果已经保存避雨版本，`rain` 为对应栅格对象。

### 5.2 获取单个版本

```http
GET /api/surface-networks/default
GET /api/surface-networks/rain
```

普通版本由服务端当前加载的 `campus.grid` 直接提供。避雨版本不存在时返回：

```json
{
  "grid": null,
  "updatedAt": 0,
  "available": false
}
```

### 5.3 保存避雨版本

```http
PUT /api/surface-networks/rain
Authorization: Bearer <admin-token>
Content-Type: application/json
```

请求体：

```json
{
  "grid": {
    "x0": 121.6001,
    "y0": 31.1842,
    "dx": 0.00005,
    "dy": 0.00005,
    "rows": ["...", "..."]
  }
}
```

服务端会校验：

1. 坐标参数是有限数字；
2. `x0/y0/dx/dy` 必须和普通路网一致；
3. 行数必须一致；
4. 每行列数必须一致；
5. 避雨路网格子只能使用 `0` 或 `1`；
6. 请求必须经过管理员鉴权。

写入前会对运行中的 SQLite 数据库执行 online backup，并检查备份的 `PRAGMA quick_check`；之后在事务中更新记录。为避免多个连接同时写 `static.db` 导致前端长时间阻塞，保存流程采用「短 busy_timeout + 多次尝试 + 尝试之间让出事件循环」的策略：

- 最长约 2 秒内给出结论；
- 如果仍然拿不到写锁，返回 `503` 并附带可操作的错误信息；
- 前端收到 `503` 会自动重试一次。

## 6. 前台导航流程

### 6.1 初始化

`src/lib/store.ts` 启动时加载：

1. `/data/campus.json`，得到普通路网；
2. `/api/surface-networks/rain`，尝试加载避雨版本；
3. 普通路网加载后调用 `initRouting()`；
4. 避雨版本存在且校验通过时，启用“我要避雨！”开关。

后端不可用或避雨版本不存在时，普通导航仍可使用。

### 6.2 切换模式

切换“我要避雨！”时：

**正式逻辑（当前测试版未启用）**：

1. 保留当前起点和终点；
2. 选择普通或避雨栅格；
3. 重新调用 `initRouting()`；
4. 重建 `route.ts` 内部的可走格数组；
5. 重新计算当前路线；
6. 递增路网版本号，触发 MapView 重绘蓝色路网。

**测试版临时逻辑**：

1. 保留当前起点和终点；
2. 设置 `rainMode = true`；
3. 重新调用 `initRouting()`，并把地下地图中连通地面的 `ramp` 连接点坐标作为 `extraWalkable` 传入，使这些车辆出入口在地面栅格中也可走；
4. 调用 `findIntegratedRoute(..., { forceUnderground: true })`；
5. 触发 MapView 重绘地面段（蓝色）和地下段（紫色）。

`route.ts` 使用模块级路由状态，因此不能只修改 Vue 中的 `campus.grid`。每次版本切换都必须重新初始化路由器。

### 6.3 地面寻路

地面路网仍使用 8 邻接 Dijkstra：

```text
上、下、左、右、左上、右上、左下、右下
```

每个可走格是一个节点，相邻可走格之间自动形成连接。直行和斜行按实际地理距离计算。

避雨模式不会修改：

- Dijkstra 算法；
- 格子之间的距离；
- 步行速度；
- 起点和终点吸附规则；
- 路径平滑逻辑。

它只修改参与寻路的可走格集合。

### 6.4 地下路线

地下路线继续使用地下地图中的 `nodes + edges`。切换避雨模式后，地面到地下连接点的接驳部分会使用当前选中的地面栅格；地下部分仍使用独立地下图。

**测试版临时逻辑**：当 `forceUnderground: true` 时，不再比较地面直达与地下候选，而是固定按以下步骤生成路线：

1. 枚举所有连通地面与当前地下楼层的连接点（`connectors`），包含 `ramp`、`stairs`、`elevator`；
2. 分别计算从起点到每个连接点的地面距离，取最小值作为**进入点**；
3. 分别计算从每个连接点到终点的地面距离，取最小值作为**退出点**；
4. 在地下路网中计算进入点到退出点的最短路径；
5. 拼接为「地面 → 地下 → 地面」三段路线；
6. 若进入点与退出点为同一点，或二者在地下路网中不可达，则回退到枚举所有组合并选总距离最短的候选。

蓝色表示地面，紫色表示地下，并显示进出连接点。避雨模式只影响地面部分（含临时开放 `ramp` 可走栅格），不影响地下路径的选取与显示。

## 7. 地面路网显示

“显示统一地面路网”显示的是当前选中版本的全部可走栅格连接：

- 普通模式显示普通栅格；
- 避雨模式显示避雨栅格；
- 所有连接统一使用蓝色；
- 不再区分蓝色/青色遮雨属性，也不区分道路来源。

`walkablePaths()` 与 `findRoute()` 使用同一个内存栅格：

```text
图层显示：遍历当前版本的全部 8 邻接连接
导航计算：在当前版本中寻找起点到终点的最短路线
```

因此打开路网显示后，看到的就是当前导航算法所使用的地面路网，而不是另一份仅用于展示的数据。

## 8. 后台编辑器

相关文件：

```text
src/admin/RainNetworkWorkspace.vue
src/admin/rainStore.ts
src/lib/network.ts
```

### 8.1 编辑流程

1. 登录管理后台；
2. 进入“避雨路网”；
3. 加载已保存的避雨版本；
4. 如果尚未保存，则从普通路网复制一份作为草稿；从普通路网复制草稿时会把可走字符统一成 `0`（`toRainDraft`），因此保存的避雨版本只含 `0/1`；
5. 使用画布编辑格子；
6. 点击“保存避雨版本”。

编辑器不会直接修改普通路网、地下路网、地点数据或旧遮雨属性字段。

### 8.2 编辑工具

编辑器底图始终显示，且与前台共用 `createCampusMap`（BaiduCRS + 百度瓦片），因此栅格与瓦片、校园轮廓使用同一套投影。

- **画笔 · 可走**：把格子设置为 `0`；只能涂抹在普通路网原本可走的格子上，不能凭空创造新的雨天路径；
- **擦除 · 不可走**：把格子设置为 `1`；可以涂抹在任意格子上；
- **平移地图**：只有切到该工具时才能拖动地图，此时不涂格；画笔/擦除模式下会禁用地图拖拽、框选缩放和双击缩放，避免同一次拖动既平移又涂格，滚轮缩放和双指缩放始终可用；
- **画笔大小**：可选择 `1×1`、`3×3`、`5×5`、`7×7`、`9×9` 方形画笔，以落点为中心覆盖对应区域，便于快速标记大片露天或连廊区域；
- **撤销**：恢复上一次栅格快照；
- **重做**：恢复已撤销的栅格快照；
- **放弃修改**：回到最近一次加载或保存的版本；
- **保存避雨版本**：通过管理员 API 写入静态数据库。保存时如果遇到数据库写锁被占用，前端会自动重试一次，按钮会显示“重试中…”。

编辑器用一个自定义 Leaflet canvas 图层（`L.Layer.extend`）按当前视野裁剪绘制栅格，只画可见格子，避免为数万个格子创建独立 Leaflet 图层。图层只持有 `() => rain.grid` 这样的 getter，不持有栅格快照，因为每次落笔都会整体替换 `rain.grid` 对象。canvas 通过 `L.DomUtil.setPosition(canvas, map.containerPointToLayerPoint([0, 0]))` 钉在图层坐标系，因此平移/缩放后与瓦片和校园轮廓保持对齐；编辑器地图以 `zoomAnimation: false` 创建，缩放瞬时完成，避免动画期间自绘图层与底图短暂错位。鼠标与触控拖动均可连续涂格，大画笔沿拖动路径连续覆盖，越界格子自动裁剪。可走格和不可走格使用半透明色，以免遮挡地图细节。

### 8.3 未保存保护

存在未保存修改时：

- 后台切换页面会提示确认；
- 浏览器关闭或刷新会触发离开提示；
- 保存按钮只在管理员登录且存在修改时可用。

当前保存接口采用最后一次写入覆盖策略，尚未实现多管理员并发版本冲突检测。

## 9. 数据安全和运维

### 9.1 不直接编辑 SQLite 文件

应通过后台编辑器或 API 修改避雨路网，不应直接编辑 `static.db` 的 WAL 文件或手工改写数据库。

### 9.2 备份和完整性

修改静态数据库前应：

1. 确认没有旧服务实例并行写库；
2. 使用 SQLite online backup；
3. 对备份执行 `PRAGMA quick_check`；
4. 在事务中写入；
5. 必要时执行 WAL checkpoint；
6. 再检查数据库完整性。

### 9.3 静态数据库与 Git

`static.db` 是地图静态数据的一部分，可以由 Git 跟踪。管理员保存避雨路网后，数据库会产生工作区修改；提交前应确认：

```bash
git status --short server/static.db
git diff --check
```

动态数据库、旧数据库、日志和临时备份不应随意提交。

## 10. 当前限制

1. 避雨路网是完整栅格副本，保存时提交整个 `rows`，不是增量补丁；
2. 没有自动判断哪些格子有雨棚，路径是否适合避雨完全由管理员编辑；
3. 当前 8 邻接规则允许部分对角线切角，避雨路网也沿用此行为；
4. 删除格子可能导致建筑入口、地下连接点或区域不可达，保存前尚未提供完整的全图连通性分析；
5. 多个管理员同时编辑时，后保存者可能覆盖先保存者；
6. 避雨版本主要通过 API 获取，服务端不可用时前台会退回普通路网；
7. 地下路线仍受现有一次进入、一次退出的集成算法限制；
8. 旧数据迁移脚本只清理字段，不重新生成或校验避雨路网内容，迁移后仍需管理员按需维护 rain 版本；
9. **测试阶段**：当前「我要避雨！」导航尚未真正使用 `rain.grid`，而是强制走地下路线。该逻辑仅用于快速验证，后续会切回正式的避雨栅格导航；临时逻辑可能导致以下问题：
   - 地下路网不覆盖的区域无法提供避雨方案；
   - 距离最近但地下段绕远的出入口会被优先使用，总距离可能不是最短；
   - 车辆坡道（`ramp`）在地面栅格中被临时开放为可走，普通模式下不会生效。

## 11. 测试重点

应覆盖以下行为：

- 普通路网和避雨路网的坐标参数一致；
- 非法行数、列数、字符不能保存；
- 未登录不能保存；
- 没有避雨版本时前台开关不可用；
- 保存避雨版本后前台可以加载；
- 切换避雨模式会重新计算路线；
- 路网显示与当前寻路版本同步；
- 关闭避雨模式后恢复普通路线；
- 撤销、重做和放弃修改保持栅格一致；
- 普通路网草稿中的 `2` 会被规范化为 `0`，保存不会被服务端拒绝；
- 保存不修改普通路网和地下路网；
- `scripts/remove-rain-data.mjs` 能正确移除废弃遮雨字段且不改动其他数据；
- 数据库写锁场景下保存能正确返回 503 或自动重试，不会长时间阻塞前端；
- 测试版临时逻辑：`forceUnderground` 时使用最近出入口，地下不可达时回退枚举；
- `ramp` 连接点在 rainMode 下被临时加入地面可走栅格，普通模式下不影响导航。

当前实现的服务端、前台、构建测试以及迁移脚本测试均已通过；后续如果增加连通性检查或并发控制，应同步扩展本设计文档。
